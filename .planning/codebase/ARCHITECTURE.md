## Pattern Overview

**Overall:** Configuration-driven Docusaurus documentation site with progressive book/section nesting and shared component layer.

**Key Characteristics:**
- **Registry-driven structure**: Books and their metadata live in one `books.js` file; sidebars auto-generate from directory names (via Docusaurus autogenerated feature)
- **Two-level nesting**: Books → Sections (numbered directories), each section → pages (numbered files); Docusaurus position numbers drive ordering
- **Shared component layer**: Custom components (YouTube, ExpandableCode, TableWrapper) registered globally in MDXComponents, available to all pages
- **Token-based theming**: All colors/spacing come from DWC CSS custom properties (`--dwc-*`) in `dwc-ui.css`; Docusaurus Infima tokens map to DWC tokens
- **Static theme assets**: Fonts (Inter, JetBrains Mono) and vendor CSS self-hosted; no CDN dependencies
- **Throwing build gates**: Broken links, anchors, images, and Markdown links fail the build (enforced in docusaurus.config.js)
- **BBj language support**: Prism grammar extended for BBj keywords verified against BBj MCP

## Layers

**Landing Page Layer:**
- Purpose: Single entry point for all users; book discovery and navigation
- Location: `docs/src/pages/index.js`
- Contains: React page component that reads `books.js` and renders cards
- Depends on: `src/data/books.js` (book metadata)
- Used by: Docusaurus router (renders at `/Courses/`)

**Navigation & Configuration Layer:**
- Purpose: Book-level organization; sidebar structure; site-wide Docusaurus configuration
- Location: `docs/sidebars.js`, `docs/docusaurus.config.js`, `docs/src/data/books.js`
- Contains: Per-book sidebar definitions (autogenerated from dir names), docusaurus plugins/themes/presets, book registry with icons and labels
- Depends on: Directory structure under `docs/docs/`
- Used by: Docusaurus build system; navbar rendering

**Book & Section Layer:**
- Purpose: Organize content into named sections with subsection pages
- Location: `docs/docs/<book-id>/<N>-<section-name>/` directories
- Contains: `_category_.json` (section metadata), numbered `.mdx` files (pages)
- Depends on: MDX component registry (for DocCardList, exercises, etc.)
- Used by: Docusaurus sidebar generation; page routing

**Content Page Layer:**
- Purpose: Individual lessons, exercises, resources within a section
- Location: `docs/docs/<book-id>/[<N>-<section>/]<NN>-<page>.mdx` or top-level book pages (overview, exercises, etc.)
- Contains: MDX with frontmatter (title, description), H2+ headings, Markdown, custom components, code fences
- Depends on: MDX component registry, examples in `docs/examples/`, samples in `docs/static/files/`
- Used by: Docusaurus page rendering; browser

**Component & Styling Layer:**
- Purpose: Reusable UI components, theme variables, Prism syntax highlighting
- Location: `docs/src/components/`, `docs/src/theme/`, `docs/src/css/`, `docs/static/css/`
- Contains: YouTube, ExpandableCode, TableWrapper React components; MDXComponents registry; Prism BBj grammar; SCSS with DWC token CSS vars; vendored dwc-ui.css
- Depends on: Docusaurus theme, React, Prism.js
- Used by: All content pages; theme rendering

**Static Assets & Examples Layer:**
- Purpose: Vendored code, downloadables, brand assets
- Location: `docs/examples/<book-id>/`, `docs/static/files/<book-id>/`, `docs/static/img/`, `docs/static/js/`, `docs/static/css/`
- Contains: `.bbj` sample files (kept in sync with downloadable zips), logos, favicons, fonts, theme switcher script, link decorator script
- Depends on: Nothing (static)
- Used by: Content pages (code samples, downloads, images, scripts)

## Data Flow

### Primary Request Path (Book Page Load)

1. Browser requests `/Courses/docs/<book-id>/<section>/page` (or `/Courses/` for landing)
2. Docusaurus router matches against autogenerated sidebar from `docs/docs/<book-id>/` directory structure
3. MDX page file is loaded (`docs/docs/<book-id>/<N>-section/<NN>-page>.mdx`)
4. MDX is parsed; custom components are looked up in MDXComponents registry (`docs/src/theme/MDXComponents.js`)
5. Content renders using Docusaurus Layout; applies `custom.scss` with DWC token variables
6. JavaScript (theme switcher, link decorator) loads from `docs/static/js/`
7. CSS (dwc-ui.css, fonts) loads from `docs/static/`; Prism highlights code blocks with BBj grammar
8. Page renders to browser

### Example Rendering Flow (YouTube Component)

1. Author writes `<YouTube id="..." title="..." />` in a .mdx file
2. MDX parser encounters the tag
3. MDXComponents registry resolves `YouTube` → `docs/src/components/YouTube/index.js`
4. YouTube component renders a privacy-enhanced iframe (does not fetch video until user clicks)
5. Styles from `docs/src/components/YouTube/styles.css` apply; respects light/dark mode via DWC tokens

### Code Example Flow (ExpandableCode)

1. Author writes a code fence ```` ```java ... ``` ```` > 40 lines
2. Docusaurus Prism renderer wraps it in ExpandableCode if detected
3. ExpandableCode shows first 10 lines; user clicks "Expand" to reveal full code
4. Styles from `docs/src/components/DocsTools/ExpandableCode/styles.css` apply

### Build-Time Validation Flow

1. Developer runs `npm run build` in `docs/`
2. Docusaurus collects all .mdx files from `docs/docs/<book-id>/`
3. For each markdown link, anchor, image:
   - If broken: throw error (configured via `onBrokenLinks: 'throw'`, `onBrokenAnchors: 'throw'` in docusaurus.config.js)
4. For images:
   - If referenced in markdown but file missing: throw error
5. Build succeeds only if all gates pass
6. Output written to `docs/build/`

**State Management:**
- **Theme state**: Stored in localStorage by `docs/static/js/dwc-theme-switcher.js`; persists across sessions
- **Search state**: Local search index built at build time by `@easyops-cn/docusaurus-search-local` plugin
- **No runtime state**: Docusaurus generates static HTML; no backend state

## Key Abstractions

**Book:**
- Purpose: A collection of sections and metadata representing a coherent training topic
- Examples: `src/data/books.js` defines intro-bbj and dwc books
- Pattern: Defined as an object with { id, title, navLabel, icon, description, to } in books.js; auto-routed by Docusaurus

**Section:**
- Purpose: A logical grouping of related pages within a book
- Examples: "Getting Started", "DWC Controls"
- Pattern: Numbered directory `<N>-<kebab-case-name>` under `docs/docs/<book-id>/`; contains `_category_.json` (metadata) and numbered pages

**Page:**
- Purpose: A single lesson or resource (Markdown rendered as HTML)
- Examples: "01-setup.mdx" (first lesson), "90-exercise-tic-tac-toe.mdx" (exercise)
- Pattern: `.mdx` file with YAML frontmatter (title, description, sidebar_position); lives in a section directory or at book root

**Exercise:**
- Purpose: A practice task embedded in a page or as a standalone page
- Pattern: `:::exercise` admonition or a `9N-exercise-*.mdx` page with task description and (later) solution pointers

**Example/Sample:**
- Purpose: Copy-paste-ready BBj or DWC code illustrating a concept
- Location: `docs/examples/<book-id>/<section-abbrev>/FileName.bbj`; mirrored as downloadable zip in `docs/static/files/<book-id>/`
- Pattern: File verified with `bbj_check_syntax` before committed

## Entry Points

**Landing Page:**
- Location: `docs/src/pages/index.js`
- Triggers: Browser request to `/Courses/` (baseUrl)
- Responsibilities: Render book cards from `src/data/books.js`; link each to `/Courses/docs/<book-id>/overview`

**Book Root:**
- Location: `docs/docs/<book-id>/00-overview.mdx`
- Triggers: Click on book card; browser request to `/Courses/docs/<book-id>/overview`
- Responsibilities: Overview, book description, links to sections via DocCardList component

**Section Index:**
- Location: `docs/docs/<book-id>/<N>-section/index.mdx`
- Triggers: Click on section in sidebar; browser request to `/Courses/docs/<book-id>/<section>/`
- Responsibilities: Section intro, links to all pages in section via DocCardList

**Page:**
- Location: `docs/docs/<book-id>/<N>-section/<NN>-page>.mdx`
- Triggers: Click on page in sidebar; browser request to `/Courses/docs/<book-id>/<section>/<page>`
- Responsibilities: Content (lessons, exercises, code samples, videos, images)

## Architectural Constraints

- **BaseUrl is fixed:** `/Courses/` (configured in docusaurus.config.js). All links, CSS, JS paths must account for this.
- **Books are immutable once ID is assigned:** The id (intro-bbj, dwc) becomes a permanent URL slug; changing it breaks all deep links. New books must use new slugs.
- **Sidebars are autogenerated:** Directory structure (numbers, names) directly determines sidebar order and labels. Manual sorting in sidebars.js is not used.
- **No client-side routing state:** Docusaurus generates static HTML; theme state (light/dark) is localStorage-based only; no page-level state persists.
- **Docusaurus 3.10.2 exact pins:** All @docusaurus/* packages pinned to 3.10.2; breaking compatibility with versions outside this range (package.json).
- **Node 24 required:** Specified in `docs/.nvmrc` and package.json engines field; CI uses this version (GitHub Actions).
- **MDX component registration is global:** Components in MDXComponents apply to all pages; no per-page or per-book overrides. To customize for one book, use inline conditional styling via CSS classes, not component swapping.
- **DWC token CSS is vendored:** `docs/static/css/dwc-ui.css` is a snapshot from webforJ; it is not auto-updated. Manual updates required if webforJ tokens change.
- **Fonts are vendored:** @fontsource-variable packages are bundled at build time. Changing font families requires editing package.json and custom.scss.
- **Prism BBj grammar is extended:** `docs/src/prism/bbj-extend.js` adds BBj-specific tokens to Prism's grammar. Changes must be verified against BBj MCP before committing (documented in CLAUDE.md).
- **Build gates are strict:** onBrokenLinks, onBrokenAnchors, onBrokenMarkdownLinks, onBrokenMarkdownImages all set to 'throw'. Development must fix any issues before build succeeds.

## Anti-Patterns

### Hardcoding Colors in SCSS

**What happens:** A developer writes `color: #0066cc;` in a .scss file instead of using `var(--dwc-color-primary-text)`.

**Why it's wrong:** Hardcoded colors break dark/light mode theming. Readers in dark mode see unreadable text. Updating the brand requires manual search/replace across files.

**Do this instead:** Always use `--dwc-*` CSS custom properties from `docs/static/css/dwc-ui.css`. Check available tokens in the file header, or search for `--dwc-` in `docs/src/css/`.

Example:

```scss
/* ❌ Wrong */
.my-box { background: #f5f5f5; color: #333; }

/* ✅ Correct */
.my-box { background: var(--dwc-surface-2); color: var(--dwc-color-text); }
```

### Using `<>` for fragments instead of `<React.Fragment>` in custom components

**What happens:** A React component uses `<>...</>` syntax, which fails during server-side rendering or when Docusaurus swizzles the component.

**Why it's wrong:** Docusaurus uses MDX which may have stricter fragment handling; TypeScript in future may require named fragments for clarity.

**Do this instead:** Use explicit `<React.Fragment>` or import Fragment from react.

Example in `docs/src/components/YouTube/index.js`:

```javascript
/* ❌ Avoid */
return <>{content}</>;

/* ✅ Correct */
import { Fragment } from 'react';
return <Fragment>{content}</Fragment>;
```

### Absolute file paths in MDX image references

**What happens:** Author writes `![alt](/img/screenshot.png)` instead of `./img/screenshot.png` relative to the markdown file.

**Why it's wrong:** Relative links are portable; if a section is moved, relative links still work. Absolute links break. The build gate (onBrokenMarkdownImages: 'throw') will catch this, but relative is the right pattern.

**Do this instead:** Use relative paths from the markdown file to the image.

Example in a page at `docs/docs/dwc/01-section/01-page.mdx`:

```markdown
/* ❌ Wrong; breaks if section is renamed */
![Example](./../../static/img/example.png)

/* ✅ Correct; relative to the markdown file */
![Example](./img/example.png)
```

Then place the image at `docs/docs/dwc/01-section/img/example.png`.

### Forgetting to add language identifier to code fences

**What happens:** Author writes a code fence without specifying language: ```` ``` ... ``` ````.

**Why it's wrong:** Without a language, Prism cannot syntax-highlight. For BBj code, keyword highlighting is essential for learning. Also, the build doesn't validate syntax if language is missing.

**Do this instead:** Always include language: ```` ```bbj ... ``` ````, ```` ```java ... ``` ````, ```` ```css ... ``` ````, etc.

Example in any .mdx:

```markdown
/* ❌ Wrong; no syntax highlighting */
    ...some code...

/* ✅ Correct */
\`\`\`bbj
PRINT "Hello, BBj"
\`\`\`
```

### Adding webforJ-specific components (ComponentDemo, DocChip, JavadocLink)

**What happens:** A contributor copies ComponentDemo, DocChip, or JavadocLink from webforJ/webforj-documentation.

**Why it's wrong:** These components are tightly coupled to webforJ's architecture (MUI, i18n, Giscus, Maven). They introduce dependencies that don't apply to a training site for BBj/DWC, bloat the site, and create maintenance burden (we'd need to track webforJ changes).

**Do this instead:** Use only the generic Docusaurus components (DocCardList, Tabs, TabItem) and the custom BASIS components (YouTube, ExpandableCode, TableWrapper). For new needs, author a new minimal component.

### Storing secrets or credentials in examples

**What happens:** A sample file includes an API key, database connection string, or password.

**Why it's wrong:** Public examples are published to GitHub and the web; credentials are exposed. Anyone can abuse the credentials.

**Do this instead:** Never include real credentials. Use placeholder strings like `"YOUR_API_KEY"`, `"<password>"`, or example values like `"localhost"`, `"demo_user"`. Document that the reader must substitute their own.

Example:

```bbj
/* ❌ Wrong */
USERNAME = "admin"; PASSWORD = "super_secret_2024"

/* ✅ Correct */
USERNAME = "YOUR_USERNAME"; PASSWORD = "YOUR_PASSWORD"
```
