## Summary

The relocation is mechanically small and low risk. I did a full trial in a scratch copy (`/private/tmp/claude-501/.../scratchpad/trial`, not in the repo): copied the 26 `.md` pages and 48 images, converted image syntax and links, added `_category_.json` per chapter, and ran `docusaurus build`. All 26 pages compile as MDX unchanged (no curly-brace or `<` problems), the build produced 27 dwc sitemap routes (26 old content routes plus `/docs/dwc/overview`) with slugs identical to the old site, and the old-vs-new anchor comparison found 307 old heading anchors with exactly 1 missing (`ready-to-get-started` on the old root page, which D-09 intentionally drops). Vale at error level on the unmodified relocated pages reports only 37 errors in 13 files (see Vale section); warnings (440) and suggestions (56) do not gate.

Three findings change or sharpen the CONTEXT decisions and need a planner decision: (1) a bare `<DocCardList />` on the overview works but renders 16 cards including a card that links to the overview itself, and it takes card text from each page's front matter `description` (so D-07 descriptions become visible text; chapter cards without a description show the page's first paragraph); (2) a Markdown link `[x](/files/dwc/a.zip)` is rewritten by Docusaurus into a hashed `/assets/files/a-<hash>.zip`, so the stable URL needs the `pathname:///files/dwc/a.zip` form; (3) the Phase 1 stub is referenced by `tools/prove-gates.sh`, `tools/verify-phase1.sh` and `tools/verify-phase2.sh`, which must be repointed in the same PR or they go red.

**Primary recommendation:** Write one re-runnable Python relocation script that reads from `git archive 965da6d` of `../bbj-dwc-tutorial` (not the working tree), emits commit 1, and prove "text unchanged" with a line-diff allowlist; take the snapshot first with a stdlib Python script; build sample ZIPs with stdlib `zipfile` (fixed 1980-01-01 timestamps, sorted entries, deflate level 9) and make `--check` compare logical content (names, order, CRC32, size) rather than raw bytes.

### Pattern 1: Top-level page order with chapters 01-12 (D-12) - PROVEN
Folder prefixes `01-`..`12-` map to sidebar positions 1..12, so top-level files cannot use 1-3 without colliding. In the trial, `sidebar_position: 0` (overview), `0.1` (prerequisites), `0.2` (samples), `0.3` (resources) plus chapter `_category_.json` `position: N` produced the exact order Overview, Prerequisites, Sample Code, Resources, chapters 01..12 in the rendered sidebar (checked in `build/docs/dwc/overview.html`). Fractional positions are valid. Alternative (not tested, more invasive): give the top-level files prefixed names and shift chapter positions in `_category_.json` to 5..16. Recommend fractional `sidebar_position`: no renames, URLs unchanged. Slugs: Docusaurus strips `NN-` prefixes, so the chapter pages keep identical slugs and `00-overview.mdx` yields `/overview`.

## Common Pitfalls

### Pitfall 1: `.md` files are parsed as MDX
**What goes wrong:** curly braces, stray `<tag>` outside fences, or `{#id}` misuse fail compilation.

**What goes wrong:** On `00-overview.mdx` it renders cards for all 16 top-level sidebar siblings including a card that links to the page itself ("Overview"). ## Samples sync design (`tools/sync-samples.py`)

Language: Python 3 stdlib. [VERIFIED by prototype] Per-book, generic:
- Inputs: for each book directory `docs/examples/<book>/` (or `<book>` CLI args).
- Outputs in `docs/static/files/<book>/`: one `<folder>.zip` per immediate subdirectory of `docs/examples/<book>/` (for dwc: 10 ZIPs named exactly as the folders, e.g. `01_GUI2BUI2DWC.zip`), plus `<book>-samples.zip` containing everything. Each ZIP includes the book's `LICENSE` and `README.md` (D-17). Suggested layout inside each ZIP: a single top-level directory (`01_GUI2BUI2DWC/` containing `LICENSE`, `README.md`, and the sample files; `dwc-samples/` for the all-in-one containing all 10 folders plus `LICENSE`/`README.md`). Pick one layout and document it in `samples.md`.
- Determinism recipe (tested: two runs identical md5; identical md5 under zlib 1.2.11 and 1.2.12):
  - `zipfile.ZipInfo(arcname, date_time=(1980,1,1,0,0,0))` (the ZIP minimum; Python rejects earlier years)
  - `create_system = 3`, `external_attr = (0o100644 << 16)` for every file (normalizes the one 755 `TreeSearch.bbj`); no directory entries
  - entries sorted by `arcname` string (codepoint order, never locale; use `sorted()` on POSIX-normalized relative paths, `/` separators)
  - `writestr(zi, data, compress_type=ZIP_DEFLATED, compresslevel=9)` (the keyword args exist on `writestr` since Python 3.7; `ZipInfo` has no `compresslevel` attribute on 3.11)
  - read file bytes in binary; skip `.DS_Store` and any dotfile; fail on symlinks
  - write via temp file and atomic replace
- Sizes: all-in-one ~77 KB deflate (213 KB stored).
- `--check` semantics (recommended): regenerate in memory and compare to the committed ZIP by the logical manifest (sorted list of `(arcname, size, crc32, date_time, external_attr)`), AND require that the set of ZIP files in `static/files/<book>/` equals the expected set (no missing, no stale, no unexpected). Exit non-zero with a readable diff. Reason: deflate output can differ if CI's zlib is zlib-ng or a future version, whereas names, order and CRC32 cannot. Optionally also report (not fail) when bytes differ but the manifest matches. If the user insists on byte-identical gating, switch to `ZIP_STORED` (platform-independent bytes), at the cost of ~3x larger downloads.
- CI wiring: `test-build.yml` runs with `working-directory: docs`; add after `npm ci`: `- run: python3 ../tools/sync-samples.py --check` (the script resolves its paths from its own location, not the CWD). `ubuntu-latest` ships python3, so no `setup-python` is required; if wanted, pin it for reproducibility. Run the check before `npm run build` so drift fails fast.
- Security: input files come only from the repo; reject path components `..`, absolute paths and symlinks when walking; never extract archives; never execute sample code.
