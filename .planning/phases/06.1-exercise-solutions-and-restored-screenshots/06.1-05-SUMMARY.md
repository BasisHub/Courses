# Phase 06.1 Plan 05: Tic-Tac-Toe family solution drafts Summary

**Staged drafts for the three Tic-Tac-Toe exercises of the intro-bbj book: a two-player game on nine buttons driven by one button callback, a standalone computer-player version whose ComputerPlayer class offers Random and MinMax behind nextMove with a list button to switch at runtime, and an OO refactor into Board, Player, GameWindow and a launcher, plus a 125-row symbol checklist.**

## Accomplishments
- `TicTacToe.bbj` creates the nine cell buttons in a loop (IDs 101 to 109, three rows of three), a status text (110) and a New game button (111), registers label callbacks and runs `process_events`. The pushed cell is `getLastEvent().getControl().getID() - 100`. The eight lines come from the table `123456789147258369159357`; the win check runs before the draw check, so a ninth move that completes a line is reported as a win. A click on a taken cell or after the end changes nothing.
- `TicTacToeComputer.bbj` is a full standalone copy with a window height of 430, a "Computer plays:" label and a list button (ID 112, items Random and MinMax). Human is X, computer is O; both moves go through one `makeMove` label so the win-before-draw order holds for both. `ComputerPlayer.nextMove(board$, strategy$)` dispatches to `randomMove` (RND over the free cells) or `minMaxMove`, which scans cells 1 to 9 and keeps a new best only on a strictly greater score, so ties go to the lowest cell and play is repeatable. `minimax` scores O win 1, X win -1, full board 0.
- The OO solution is four files in `oo-tic-tac-toe/`: `Board` (nine-character state, `place`, `getCell`, `winner`, `isFull`, `reset`, no window code), `Player` (public `Name$` and `Mark$`), `GameWindow` (controls, `show`, `onCellPush`, `onNewGame`, `onClose`, private `resetGame`; `use ::Board.bbj::Board` and `use ::Player.bbj::Player`) and `PlayTicTacToe.bbj` (launcher: new, show, `process_events`). Nothing references `TicTacToe.bbj`.
- `symbols-05.tsv` lists 125 symbol rows across all six drafts. Each source is either an OK-repo file or a documentation.basis.cloud URL fetched while drafting (getControl, getID, getLastEvent, addListButton, selectIndex, getSelectedIndex, getItemAt, BBjVector addItem and getItem, mod, int, num, dim, substrings, rnd, methodret, method scope, BBjButtonPushEvent, BBjCloseEvent).

## Needs your attention (for plan 07, orchestrator or human)
Unproven assumptions, all recorded in the TSV and in the coverage rationale:
1. **Recursion with method locals (RESEARCH A5).** `minimax` relies on each call having its own `i`, `score`, `best` and `newBoard$`. The documentation only says locals are visible inside the method; per-call isolation under recursion needs a run. If it fails, `minimax` needs a different shape (for example an explicit stack string).
2. **Comments inside class bodies.** To be safe, all `rem` lines in classes sit inside methods, never between methods or before `field`.
3. **Statement forms to confirm with `bbj_check_syntax`:** `#reset()` as a standalone call in the `Board` constructor and in `GameWindow`; `release` inside `method public void onClose(BBjCloseEvent ev!)`; `use ::Board.bbj::Board` resolution from `GameWindow.bbj` and `use ::GameWindow.bbj::GameWindow` from the launcher (same pattern as `CarApplication.bbj`, but run from the `oo-tic-tac-toe/` folder); `declare BBjVector cells!` and `declare BBjListButton strategyList!` as declare types.
4. **Reserved-word check** (`bbj_reserved_word`) for the variable names `cell`, `moves`, `score`, `best`, `pick`, `seen`, `turn$`, `a`, `b`, `c`, `k`, `s$`, `w$` and the field names `board!`, `status!`.
5. **Getters from public fields:** `getName()` and `getMark()` on `Player` are assumed generated like `setColor` in the Car sample and `#getName()` in the Payroll example of the METHOD page.
