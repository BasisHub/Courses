# Phase 06.1 Plan 06: Login dialog family solution drafts Summary

**Staged drafts for the two login exercises of the intro-bbj book: a plain-controls LoginDialog class that returns TRUE or FALSE with a masked password and a fixed error message, and a standalone ResponsiveLoginDialog that puts the same logic into a BBjChildWindow card styled by responsive-login.css (centered 22rem card from 600px up, full-screen dialog below), plus an 88-row symbol checklist.**

- **Duration:** about 10 min (ended 2026-10-04T15:57Z)
- **Tasks:** 2
- **Files created:** 4 (no file under docs/ changed)

## Accomplishments
- `LoginDialog.bbj` defines `class public LoginDialog` with private fields for the window, both edit boxes and both buttons. `show()` opens a 360 by 170 window, adds the user name box (ID 102), the password box (ID 104, flag `$0400$` for asterisks), and the Login (105) and Cancel (106) buttons, registers label callbacks `login` and `cancel` (the window close event also goes to `cancel`), and runs `process_events`. A matching non-empty pair destroys the window and does `methodret BBjAPI.TRUE`; anything else shows `msgbox("Please check your input",48,"Login")`, clears the password box and returns into the event loop. `cancel` destroys the window and does `methodret BBjAPI.FALSE`. The driver code after `classend` shows "Login accepted." or "Login canceled." and releases. The typed password is never printed, shown or logged.
- The demo pair `DemoUser$ = "demo"` and `DemoPassword$ = "bbj-demo"` are `field private static BBjString` constants under a rem comment: demo credentials for the exercise only, a real application checks a user store and never keeps passwords in its code (D-13, prohibition for EXER-04).
- `ResponsiveLoginDialog.bbj` is a standalone copy (no `USE` or `CALL` into `LoginDialog.bbj`; the header only names it as the starting point). It reads `responsive-login.css` with `Files.readAllBytes`, injects it with `BBjAPI().getWebManager().injectStyle`, opens the window with `$01101083$` and `addPanelStyle("login-screen")`, and builds the card as `addChildWindow("",$00100000$,BBjAPI().getSysGui().getAvailableContext())` with `addPanelStyle("login-card")`. Controls use the short forms; the Login button gets `setAttribute("theme","primary")`.
- `responsive-login.css` holds `.login-screen` (grid, centered, `min-height: 100vh`, `--dwc-color-primary-95` background), `.login-card` (grid, `width: 22rem`, `--dwc-surface-3`, `--dwc-shadow-m`, `--dwc-border-radius`) and one `@media (width < 600px)` block that turns the card into a full-screen dialog. The range syntax is strict: at exactly 600px the centered card applies. Only tokens declared in `docs/static/css/dwc-ui.css`, no color literal.
- `symbols-06.tsv` lists 88 symbol rows with the final `docs/examples/intro-bbj/exercises/...` install paths. Sources are OK-repo files or documentation.basis.cloud URLs fetched while drafting (FIELD verb BBj, BBjAPI constants, msgbox values, BBjControl::destroy and BBjTopLevelWindow::destroy, getText, setText, addChildWindow flags, injectStyle, setAttribute, use verb, if verb).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking, minor] Java classes through USE instead of fully qualified calls**
- **Found during:** Task 2
- **Issue:** The plan sketched `java.nio.file.Files.readAllBytes(java.nio.file.Paths.get(...))`. The only proven OK-repo pattern (DWCThemer.bbj) uses `use java.nio.file.Files` and `use java.nio.file.Paths` at the top of the file; a fully qualified static call in a class method has no precedent in the repo.
- **Fix:** Used the two `use` lines before `class public`, then `Files.readAllBytes(Paths.get(...))`. No acceptance criterion depends on the form.
- **Files modified:** ResponsiveLoginDialog.bbj

## Needs your attention (for plan 07, orchestrator or human)
1. **`return` from a callback label inside a method (RESEARCH A6).** The wrong-pair path ends with a plain `return`, written the MyDialog way. The RETURN page only describes GOSUB subroutines. A run must confirm the dialog stays open and the next push of Login is handled. If it fails, restructure with method callbacks (`setCallback(BBjAPI.ON_BUTTON_PUSH,#this!,"onLogin")`) and a state flag that lets `show()` leave `process_events`.
2. **Static field with `#` notation.** The FIELD page says static fields have getters and setters on the class name and that fields are read with `#fieldname` inside the defining class. `#DemoUser$` on a `static` field needs `bbj_check_syntax`. Fallback: drop `static`.
3. **Standalone `rem` lines between `class public` and the first `field`.** No precedent in the repo (the FIELD and USE pages only document a trailing `; rem`). If the check rejects it, move the two comment lines into the file header or onto the field lines as `; rem`. Plan 05 kept class-body comments inside methods for the same reason.
4. **Statement forms to confirm:** `if user$ <> "" and secret$ <> "" and user$ = #DemoUser$ and secret$ = #DemoPassword$ then`; `methodret BBjAPI.TRUE` from a `BBjNumber` method; `use java.nio.file.*` before the class; `new String(Files.readAllBytes(...))` inside a class method; `addEditBox(#card!.getAvailableControlID(),"",$0400$)` (signature `addEditBox(int ID, string title, string flags)` per the documentation page); `addPanelStyle` on a `BBjChildWindow` (the method sits on the BBjWindow page).
5. **Reserved-word check** (`bbj_reserved_word`) for `ok`, `choice`, `secret$`, `user$`, `note$`, `userLabel!`, `passwordLabel!`, `dlg!`, and the field names `wnd!`, `card!`.
6. **Browser run in the DWC (RESEARCH A10).** The card is a BBjChildWindow inside a window whose panel is `.login-screen`. Confirm that the child window's outer div behaves as the grid item (centered above 600px, filling the screen below) and that `width: 22rem` and `min-height: 100vh` land on the visible card. Confirm 600px exactly shows the card. The `--dwc-*` tokens come from the vendored webforJ snapshot, not from the DWC bundled with BBj.
7. **Fixed window size note.** The plain `LoginDialog` window is a fixed 360 by 170 pixel dialog; labels and boxes are positioned by pixel as chapter 1 and 2 teach.
