## Critical Issues

### CR-01: `len(a$) AND len(b$)` is a bitwise AND and rejects valid names

**Orchestrator verification (2026-10-04): REFUTED, no action.** The BBj documentation states that the logical operator `AND` returns 1 if both operands are nonzero, otherwise 0, with short-circuit evaluation; the bitwise operation is the separate `AND()` function (https://documentation.basis.cloud/BASISHelp/WebHelp/usr/Language_Concepts/numeric_operators.htm, section "Logical Operators: AND, OR"). `len(firstName!) AND len(lastName!)` is therefore a correct "both filled in" test. Kept below for the record; counted as refuted, not critical.

**File:** `docs/docs/dwc/11-advanced-responsive/90-exercise-media-queries.mdx:118` (same fence in `docs/examples/dwc/10_AdvancedResponsive/Exercise-MediaQueriesComplete.bbj:85`); also `docs/docs/dwc/08-control-validation/90-exercise-email-validation.mdx:120` (`Exercise-BuiltInValidationComplete.bbj:93`) and `docs/docs/dwc/06-flow-layouts/90-exercise-css-grid-layout.mdx:110` (`Exercise-ConvertToCssLayoutComplete-Grid.bbj:77`)
**Issue:** `if (len(firstName!) AND len(lastName!)) then` is meant as "both fields are filled in". In BBj `AND` works on the integer values of its numeric operands bit by bit (it is only a logical test when both sides are 0 or 1, as with comparison results). `len()` returns the length, so the test is the bitwise AND of two lengths: first name `John` (4) and last name `Doe` (3) give `4 AND 3 = 0`, which is false, and the form is rejected with "you didn't fill in your first and last names". `Jo`/`Smith` (2 AND 5 = 0) and `Al`/`Li` (1 AND 2 = 0) fail the same way. The email solution is worse: `(len(f) AND len(l)) AND email.trim().length()` combines three lengths bitwise. The new `Exercise-MediaQueriesComplete.bbj` was written in this phase and copied the pattern, so it is a defect introduced by the phase as well as inherited from the Moodle samples. I am about 80% sure of the BBj semantics from memory and have no BBj MCP here, so confirm with `bbj_lookup` on the AND operator before editing. The fix is harmless either way.
**Fix:**
```bbj
if len(firstName!) > 0 and len(lastName!) > 0 then
```
For the email solution:
```bbj
if len(firstName!) > 0 and len(lastName!) > 0 and e!.getText(editEmail!).trim().length() > 0 then
```
Comparisons yield 1 or 0, so the bitwise AND is then safe. Apply it to the page fence, the example file, and (via `sync-samples.py`) the ZIPs.

## Warnings

### WR-01: Email regex is invalid under the `v` flag that browsers use for `pattern`, and contains a typographic apostrophe

**File:** `docs/docs/dwc/08-control-validation/90-exercise-email-validation.mdx:97,99` (`Exercise-BuiltInValidationComplete.bbj:70,72`)
**Issue:** The value `^[\w!#$%&’*+/=\-?^_`{|}~]+(\.[...]+)*@[\w-]+(\.[\w]+)*(\.[a-z]{2,})$` is passed to the HTML `pattern` attribute. Current browsers compile `pattern` with the `v` flag. In `v` mode the characters `/ { | }` must be escaped inside a character class and a trailing `-` in `[\w-]` is a syntax error, so the pattern is invalid and the browser silently ignores it (console error, no validation). The solution therefore shows a goal-2 pattern validation that does not run. Separately, the character after `&` is U+2019 (a typographic apostrophe, copied from a web page), not ASCII `'`: `o'brien@example.com` is rejected and `o’brien@example.com` is accepted. I could not run a browser, so this rests on the `v`-mode grammar; test it in Chrome or Firefox.
**Fix:** Escape the class syntax characters and use an ASCII apostrophe, for example `^[\w!#$%&'*+\/=?^_`\{\|\}~\-]+(\.[\w!#$%&'*+\/=?^_`\{\|\}~\-]+)*@[\w\-]+(\.[\w]+)*(\.[a-z]{2,})$`. Update the `rem` tip line as well, and the starter `Exercise-BuiltInValidation.bbj` that carries the same text.

### WR-03: Five solutions use legacy `--bbj-space*` tokens that this site does not declare or check

**File:** `docs/docs/dwc/06-flow-layouts/90-exercise-css-grid-layout.mdx:61`, `91-exercise-css-flexbox.mdx:65`, `docs/docs/dwc/07-icon-pools/90-exercise-icon-static-text.mdx:50-51`, `docs/docs/dwc/05-dwc-controls/90-exercise-search-bbjtree.mdx:59`, `docs/docs/dwc/08-control-validation/90-exercise-email-validation.mdx:54`
**Issue:** `var(--bbj-space)` and `var(--bbj-space-xl)` are not declared anywhere in `docs/static/css/dwc-ui.css` (0 declarations; the file's own `.bbj-icon` rule references `--bbj-space-xs` without declaring it). If the runtime does not define them, `gap` and `padding` fall back to their initial values and the layout loses its spacing. CLAUDE.md requires `--dwc-*` tokens, and the new Phase 6.1 solutions use them (`--dwc-space-l`, `--dwc-space-xl`). `check-dwc-phase6.py solutions` validates tokens only for the ten new pages, so these older solutions are never checked.
**Fix:** Replace with declared tokens (`--dwc-space-m`, `--dwc-space-xl`), mirror the change in the example files and starters, and extend the token check in `cmd_solutions` to all 16 solution files.

### WR-04: Login screen background does not adapt to the dark theme

**File:** `docs/examples/intro-bbj/exercises/responsive-login.css:8` (fence in `90-exercise-responsive-login-dialog.mdx:120`)
**Issue:** `background: var(--dwc-color-primary-95)` is a fixed palette step (`oklch(... 99% ...)` in `dwc-ui.css`). It does not flip with `html[data-app-theme~=dark]`, so in the dark theme the card (`--dwc-surface-3`, dark) sits on a near-white screen. CLAUDE.md requires that "light and dark both work".
**Fix:** Use a mode-aware token for the screen, for example `background: var(--dwc-surface-1);`, or layer `var(--dwc-color-primary-tint)` over a surface token. Do the same for the narrow-screen rule (already `--dwc-surface-3`, fine).

### WR-05: BUI-to-DWC redirect rewrites every `apps` in the URL

**File:** `docs/docs/dwc/02-browser-developer-tools/90-exercise-theming-support.mdx:47` and the same line in the other nine DWC solution pages (`04-...:39`, `10-...:34`, `11-...:40` and `:50`, `05-...:42`, `06-...:45` and `:47`, `07-...:40`, `08-...:38`) and their example files
**Issue:** `bui!.getUrl().replaceAll("apps","webapp")` replaces all occurrences, including the host name and the app name. `https://myapps.example.com/apps/Foo` becomes `https://mywebapp.example.com/webapp/Foo`, and an app called `appsuite` is mangled. The snippet is copied into five solutions written in this phase.
**Fix:** `url! = bui!.getUrl().replaceFirst("/apps/","/webapp/")`. Update the chapter-1 boilerplate and all solutions together.
