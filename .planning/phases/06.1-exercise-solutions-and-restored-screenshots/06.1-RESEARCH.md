## Summary

The phase is content-heavy and tool-light. Six DWC pages (61, 70, 72, 73, 75, 77) already carry the Phase 6 solution block; none of the 16 pages has a pointer line yet. Ten solutions must be written as new BBj/CSS files, shown inline byte for byte, shipped in ZIPs, and covered by an extended checker. Two screenshots go back to one DWC page with an audit-row flip.

Three findings change how the plans should be written. (1) The theme `CodeBlock` wrapper already collapses every fence over 40 lines, so plain ` ```bbj title="X.bbj" ` fences are right; `ExpandableCode` (a JS template literal) would hide the code from the Python drift checker and is not what Phase 6 used. (2) The Phase 6 checkers hard-code the Phase 6 end state in many places (11 exercise pages with 6 solutions, exactly 44 `.bbj` samples in two shell scripts, an exact intro sample/ZIP file set, "(solution included)" must be absent from the intro index, ZIPs that the intro overview must link, a URL allow-list that also scans code fences); each of these breaks the moment content lands, so the checker plan must come first and edit them deliberately. (3) The Shoelace pin is `2.20.1` (npm latest, published 2025-03-11), but `ShoelaceSplitter.bbj`'s `dist/shoelace.js` URL pattern does not work for 2.20.1 in a plain browser (its chunks import bare `lit` specifiers); use the `cdn/` path. BASIS documents a better embedding route for Shoelace than the BBjHTMLView cascade: `BBjWindow::addWebComponent` + `BBjWebComponent::setCallback` (BBj 24.00+, the course minimum is 24.02).

**Primary recommendation:** Land the checker extension first (red for the new pages by design), then draft the 10 solutions in parallel by folder, run one orchestrator MCP checkpoint over all new files (Phase 6 plan 06-09 pattern, TSV evidence), then ZIP sync, then the page edits, then the shared indexes and the full gate.
