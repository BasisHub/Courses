<decisions>
## Implementation Decisions

### Locked before discussion (ROADMAP 06.1 and user feedback, 2026-10-04)
- **D-01:** Every exercise gets a solution. The ten new ones say plainly that they were written for this book, not taken from the original course.
- **D-02:** Solutions stay in the Phase 6 collapsed `<details><summary>Possible solution</summary>` block at the end of the page (P6 D-06 format: one sentence naming the files and the ZIP, then the source as titled fences, `ExpandableCode` over 40 lines). Each of the 16 pages also gets one line near the top telling the reader a possible solution is at the end of the page.
- **D-03:** Every new BBj file passes `bbj_check_syntax`, uses only verbs, functions and BBjAPI classes and methods confirmed with `bbj_lookup` after reading `bbj://primer`, and prefers BBjAPI callbacks with `process_events`. Every CSS `--dwc-*` token is verified against the DWC token catalog.
- **D-04:** `docs/examples/<book>/` is the only hand-edited copy. Inline fences are byte-identical to the files (P6 D-07), and the ZIPs under `docs/static/files/<book>/` are re-synced, including the aggregate `dwc-samples.zip` and `intro-bbj-samples.zip`.
- **D-05:** Screenshots 8B-05 (`image.png`) and 8B-07 (`image (1).png`) come back **unredacted**: the user confirmed the names and addresses are made-up demo data. They go into `docs/docs/dwc/09-*/img/` with descriptive kebab-case names and hand-written alt text (P6 D-15) in the "Printing and Print Preview" section. Their audit rows in `tools/data/dwc-gap-audit.md` change from `drop` to restored, with the reason noted.

### Open-ended exercise depth
- **D-06:** **Computer player (intro-bbj 91):** two strategies behind one method, Random and MinMax, switchable by the player (a radio button or similar control). This answers the exercise's own "Random moves, MinMax, what else?".
- **D-07:** **OO Tic-Tac-Toe (intro-bbj 02/91):** a model/view/player split: `Board` (state, rules, win check), `GameWindow` (UI and callbacks), `Player`. One sentence in the solution explains why each class exists.
- **D-08:** **Embed component (DWC 83):** embed a Shoelace component. Pick one that is not the split panel `ShoelaceSplitter.bbj` already shows. Embed it with `BBjWindow::addWebComponent` and `BBjWebComponent::setCallback` (BBj 24.00+, confirmed with `bbj_lookup`), not the `BBjHTMLView` route (user choice at plan time, 2026-10-04).
- **D-09:** **Media queries (DWC 122):** adapt the chapter 06 CSS grid sample (`docs/examples/dwc/05_CssLayouts/DWCGrid.bbj` or the grid exercise solution) so the layout changes below a breakpoint. The exercise intends a change to earlier work; the new file is a separate `...Complete` file, and the original sample stays untouched.

### Client target and chaining
- **D-10:** **Intro-bbj chapters 1 and 2 solutions are client-neutral:** plain BBjAPI controls, callbacks and `process_events`, as those chapters teach, with no CSS (CSS starts in chapter 3). They are verified to run in DWC, and the solution text says so.
- **D-11:** **Chained exercises are full standalone programs** (computer player and OO tic-tac-toe from tic-tac-toe; responsive login from login dialog). One sentence names the earlier solution they start from. No `USE` or `CALL` into the earlier file.
- **D-12:** **Responsive login dialog:** one breakpoint. Below 600px the dialog fills the screen (a `BBjChildWindow`, per the exercise hint). Above it, a centered, fixed-width card.
- **D-13:** **Login dialog credentials:** a hard-coded demo pair as a class constant, with a comment that a real application checks a user store. The class returns TRUE on accepted login and FALSE on cancel, and shows an error on a wrong pair, as the exercise specifies.

### File layout and ZIPs
- **D-14:** **DWC solutions go into the existing module folders** with the Phase 6 naming `Exercise-<Name>Complete.bbj` (plus any `.css`): 65 in `02_CSSStylesAndCustomProperties/`, 68 in `03C_Grid2GridEx/`, 83 in `09_EmbeddingOtherComponents/`. 122 and 123 go into a new `10_AdvancedResponsive/` folder with its own `10_AdvancedResponsive.zip`. Exact file names are the planner's call within this pattern. No new starter files: these exercises start from the reader's own earlier work.
- **D-15:** **Intro-bbj solutions go into one new folder,** `docs/examples/intro-bbj/exercises/`, shipped as `docs/static/files/intro-bbj/exercises.zip` and inside `intro-bbj-samples.zip`. Expected content: tic-tac-toe, computer player, login dialog, the OO tic-tac-toe class files, and the responsive login dialog with its CSS. The folder's README gets a short entry.
- **D-16:** **Multi-file solutions show every file inline,** one titled fence per file (`bbj`, `css`), each byte-identical to its example file. The P6 D-07 drift check extends per file.

### External dependencies
- **D-17:** **Shoelace (83)** loads from jsDelivr like `ShoelaceSplitter.bbj` does, but pinned to the **current stable 2.x** release, not the old `2.0.0-beta.69`. The no-CDN rule in CLAUDE.md covers the Docusaurus site, not the BBj samples readers run. The planner confirms the current 2.x version at planning time.
- **D-18:** **BBjGridExWidget (68)** assumes the plugin is installed (the exercise's first step) and that the `CDStore` demo database ships with BBj. One prerequisite sentence says so. Data access uses `SqlQueryBC(BBjAPI().getJDBCConnection("CDStore")).retrieve("SELECT ... FROM CDINVENTORY")`, as chapter 04 teaches, and passes the ResultSet to `BBjGridExWidget::setData` (amended at plan time 2026-10-04 by the user; was `sqlopen`). BBjGridExWidget API names are checked against its own documentation or source, because `bbj_lookup` covers BBj, not the plugin.
- **D-19:** **Theme (65)** ships a small hand-written theme CSS file that overrides a few `--dwc-*` palette tokens, the way a DWCThemer export would. A note says that a real DWCThemer export goes in the same place. The solution does not depend on the provisional DWCThemer link.
- **D-20:** **Light/dark switch (65)** toggles DWC's built-in light and dark themes through whatever BBjAPI call `bbj_lookup` confirms. If none exists, it sets the theme attribute on the document from BBj. The exact mechanism is verified during research, not guessed.

### Checker
- **D-21:** Extend `tools/check-dwc-phase6.py` (its `SOLUTIONS` map already takes a file list per page) and/or `tools/check-intro-bbj.py` so all 16 pages are covered: solution block present, every fence matches its file, pointer line present, starter variables and snippets exist where a starter exists. A `verify-phase6.1.sh` (or an extension of `verify-phase6.sh`) runs it alongside build, Vale and verify-phase1..6.
