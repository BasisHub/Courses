## Notes file format plan 16 must follow

The hand-written analysis lives in `tools/sample-test/report-notes.md` (the path `report.mjs` reads by default; the file does not exist yet, so every notes section shows `_To be written after the baseline run._` until plan 16 writes it).

- Four optional H2 sections, each at most once, any order: `## Static findings`, `## Draft issues`, `## Questions for Hyyan`, `## Notes`.
- Any other H2 heading aborts the report with an error naming it. Use H3 or deeper inside a section (one `### Draft: <title>` block per draft issue works well). A heading inside a code fence does not count.
- Text before the first H2 is ignored, so the file can start with instructions to the author.
- Static findings, Draft issues and Questions for Hyyan become their own report sections. `Notes` appears under Harness notes as `### Notes`, and is left out when empty.
- The text is copied as written, so it must be final Markdown: house rules apply (English, no em dash, every code fence has a language). The report is refused when the notes contain an em dash, the serial pattern (BBX and six digits), the console header label with a colon, the home folder or the admin password. Absolute paths under the repo root become `<repo>`.

## Result conventions the renderer relies on (for plans 09 and 16)

- Self-test results are matched to the four controls by the file name in `id` (`fixture/known-broken.bbj`) or, failing that, by `app` (`courses-fixture-known-broken`). The expected statuses (known-good pass, known-broken fail, known-print pass, known-missing-css fail) are a constant in `lib/report.js`; a unit test compares it with `fixtures/expected.json`.
- A behaviour result carries the manifest id of its sample in `id` and the issue number in `issue`; `category` shows up in the Outcome column as `blocked (start)`.
- Screenshot paths are relative to the results folder (as `takeScreenshots` writes them); the report prints `results/<path>`.
- Results are read from `<results>/samples`, `selftest` and `behaviour` (every `*.json`, file name order). `selftest-behaviour/` is not read.
- `compile.json` is required (`report: missing compile.json, run npm run compile`); `run.json` and `baseline.json` are optional (`not recorded` for the baseline).

## Decisions Made

- Path redaction runs on the result data before rendering and on the rendered text after it. The renderer cuts long cells at 160 characters, so a home path cut in the middle would no longer match the folder and would leave most of the user name in the report. The CLI test places the cut three characters before the end of the home folder name; with the pre-render pass disabled it fails (checked by mutation), with it in place it passes.
- The password scan fails closed: if the Java tool cannot run, the report is refused rather than written unchecked.
- `checkReportText` returns each problem once, in a fixed order: serial number pattern, serial number label, em dash, local path.
- A passing sample gets a findings block only for type-check findings or syntax errors; warnings alone (for example a title mismatch or a browser console warning) do not create a block, to keep a 63-sample report readable. Warnings still show in the block of any sample that has one.

### Additions beyond the plan (Rule 2, all covered by tests)

- **Fix:** `redactValue` redacts every string in the parsed results before `renderReport`; the text pass stays as a second layer.
- **Files modified:** `tools/sample-test/report.mjs`; test in `tools/sample-test/lib/report-cli.test.js`
- **Commit:** cc657ad

### Interpretations of unspecified details

- A file with syntax errors is a finding: it gets a findings block with a `Syntax errors` bullet even when it has no run result. The plan named only run status, behaviour outcome and type-check findings as triggers.
- Type-check Message cells carry the severity as a prefix (`warning: ...`) instead of a fifth column.
- The Runnable programs summary row reads `63 (n not run)` when some programs have no result, so a subset run is not mistaken for a full one.
- `renderReport` takes an optional second argument `{ ignored }` (default `IGNORED`) so a test can prove the pattern list renders; the notes argument may be the Markdown text or the object `splitNotes` returns.
- The Errors and Issues cells are empty when there is nothing to show; the Behaviour cell says `none` as the plan requires.
