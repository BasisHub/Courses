## Difference from the spike: 8 findings, not 6

The plan expected 6 findings in 2 files. The run shows 8 in 4 files. The extra two are real parser output, not a parser fault:

- Both are `css! = new String(Files.readAllBytes(Paths.get(BBjAPI().getFileSystem().resolvePath(...))))`. The type checker cannot choose between the `String(byte[])` and `String(String)` constructors, so its message is just `Ambiguous signatures ...`.
- Four more files use the same statement with `fs!` (an undeclared variable), five statements in all: `DWCThemer`, `DWC_ExternalCSS/Sample`, `Exercise-ThemingSupportComplete` (two lines) and `ResponsiveLoginDialog`. Their error text also contains `Paths.get(<undeclared>)`, so the contract counts them as follow-ups. The two chapter 10 files do not use an undeclared variable, so the bare message reaches the findings.
- The report (plan 07) should present these two as "type checker cannot resolve the String constructor" and not as a void bug. Whether the programs run is the baseline's job (plan 16): `Exercise-ButtonTransitionComplete` and `Exercise-MediaQueriesComplete` are windows in the manifest.
- The spike's own raw output gives the same numbers: `parseCompileOutput` over `spike/compile-all-raw.txt` returns 489 errors, 1343 warnings, 481 follow-ups and 8 findings. The plan's "six" came from reading the spike too loosely, not from a different compiler result.
- The spike's per-file table `compile-all.txt` sums to 490 errors and 1347 warnings. Three of its rows differ from the parser (TreeSearch, DWCFlexbox, DWCFlexbox.BBj24) because its line-based count matched the words `error` and `warning` inside statement text: `TreeSearch.bbj` line 110 contains `color-warning-25` and `error message`, `DWCFlexbox.bbj` line 396 and `DWCFlexbox.BBj24.bbj` line 376 contain `color-warning-50`. The parser reads only the record header, so each record counts once, at its real severity.
- 23 of the 1343 warnings are not undeclared-variable warnings (for example `Autocast from BBjServerEvent to BBjEditModifyEvent may fail at runtime` in `CSSCustomProperties`, `Exercise-ThemingSupportComplete`). They sit in `warnings` and are not findings, as the contract says (findings come from error records only). Plan 07 can list them if it wants.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug in the plan] `resultsDir('compile.json')` would create a folder**
- **Found during:** Task 2
- **Issue:** `lib/paths.js` `resultsDir(...sub)` joins the arguments, runs `mkdirSync` on the result and returns it, so `resultsDir('compile.json')` creates a directory named `compile.json`. ## Decisions Made

- `undeclared` counts error-level follow-ups only. The contract left open whether warnings (`Undeclared variable: x!`, 1320 of them) count too; counting errors only gives a clean identity (`errors = findings + undeclared`) and matches the "about 470" figure in the research notes (481 now).
- `summarizeTypecheck` ignores records with `typecheck: false`. A file with a syntax error already shows up in `syntax`, and counting it again as a type-check finding would double it.
- A record that never reaches its tail (or does not match the record pattern) is returned in `other` instead of being dropped; `compile.mjs` prints each such line as `NOTE <id>: unparsed compiler output: ...`. The real run printed none.
