<behaviour_rules>
1. Use only `behaviourTest` and `BlockedError` from '../../lib/behaviour.js', `expect` from '../../lib/fixtures.js', helpers from '../../lib/dwc.js' (readDialogs, clickDialogButton, panelStyle, cssVar, iconReport, readConsole, consolePresent, settle) and parseConsole from '../../lib/console.js' (for programs that print a result after their dialog closes). Define any other helper inside your own spec file.
2. Do not edit lib/*, playwright.config.js, manifest.json, other plans' spec files, or anything under docs/. If shared code blocks you, make the affected test throw BlockedError with the reason and list the problem under "Harness issues" in the SUMMARY.
3. The course page is the spec. For each sample, read the page sections that describe it (manifest `pages`, then `grep -n "<FileName>" <page>`), and write 1 or 2 tests per sample (at most 2, W7) that check what the page says the program shows or does. Put the claim in the title in short form. Assert only what the page claims; add other observations with note().
4. Titles: behaviourTest(id, '<claim>', opts, body) with the manifest id. Every window entry in scope gets at least one test.
5. Find controls by role and visible text. Never rely on generated ids or classes and never add hooks (D-08). Message boxes: readDialogs(page) and clickDialogButton(page, name).
6. Red tests are findings. Never weaken an assertion to make a sample pass; never skip a test.
7. Live run: `npx playwright test tests/behaviour/intro-bbj.spec.js --project=samples --reporter=line`, then `node cleanup.mjs`.
8. Timeouts (W6): the wrapper races each test body against a deadline 15 s below the test timeout and records a test that hits it as fail with category timeout; that is a finding. Do not raise timeouts or split a check to avoid it.
</behaviour_rules>
