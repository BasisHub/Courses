## What the tests say about the book

- **UAT tests 6, 7, 8, 9 and 10 are now repeatable.** The two-player rules (alternation, win, ninth-move win, draw, occupied cell, New game) hold for `TicTacToe.bbj` and the object-oriented version alike, including the `use ::Board.bbj::Board` style references resolved from the program folder (test 9). The computer player answers with a legal move under both strategies, the list switches while playing, and MinMax did not lose in four deterministic games (test 7; this is a sample of games, not a proof, and the A5 question about recursive local variables is answered only as far as four games go). The login dialog and the responsive card behave as test 8 and test 10 record. The responsive card also shows that `resolvePath("responsive-login.css")` found the CSS file in this setup (the card is a grid with rounded corners at 600 px and wider), so open questions A3 and A6 held here.
- **Not covered:** UAT test 8 also names closing the window as a way to return false; the tests use Cancel only. No test drives the Escape key or the window close button.
- **The page listing and the lesson-start file differ.** `03-developing-for-the-web.mdx` prints `Vorname:`, `Name:` and the greeting `"Hello "`; the downloadable `dwc-lesson-start/Sample.bbj` has `Firstname:`, `Lastname:` and `"Hallo "`. The test asserts only what both versions share (title "Hello World" and the typed names) and notes the difference.
- **The lesson-result program does not load its CSS file.** The page registers `sample.css` in Enterprise Manager; the program only adds the class. Run alone (as the harness does), the panel computes `display: block` and the form is not a grid. The test therefore applies the sample's own CSS text in the browser after it asserted what the program sets itself. This agrees with the manifest note for the entry.
- **The responsive card is taller than the screen on a phone.** At 599 and 500 px the card is 848 px tall in an 800 px viewport (`min-height: 100vh` plus 24 px padding on each side in a content-box card), and 1 px narrower on each side than the viewport (the child container's thin border). It fills the screen within the test's 4 px tolerance on the width; the 48 px of extra height is noted, not asserted. Not checked: whether the page scrolls.
- **A random computer can lose.** In one run the Random strategy lost the game in which X took the lowest free cell. The test asserts a result, not a winner.

## Harness issues

None that blocked anything; nothing under `lib/` was changed.

- A BBj callback sets the cell text before the status line, so a read right after the mark appeared sometimes sees the old status. The tests wait for the expected status (`statusAfter`); a future test of a program that updates several controls in one callback should do the same.
- Cell buttons with no text have an empty accessible name; they are found in DOM order below `dwc-window-content`. The window's own minimize, maximize and close buttons are outside that panel, so `page.getByRole('button')` without the panel would shift every index by 3.
- A password edit box (flag `$0400$`) is a `textbox` for Playwright (in DOM order, so the second box of a login dialog) and also an `input[type=password]`.
- A `BBjListButton` renders as `dwc-choicebox`. Its options appear only after the host is clicked (`getByRole('option')`), and the selected name is read from `[part=button-label]` in its shadow root; `textContent` of the host is empty.
- The page title of a window program equals its BBj window title (`Hello World`, `Your Input`, `Login`, `Tic-Tac-Toe`).
- `note()` cuts each note at 200 characters and the wrapper cuts the evidence at 700 (as plans 12 to 14 found); the long game boards are written as one short string per board.
- `check-behaviour.mjs --prefix <p>` prints the number of all behaviour tests found (106), not the number under the prefix (as plans 10 to 14 noted).
