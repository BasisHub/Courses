## Issue #6 evidence (for Eric)

Issue #6: "Icon Buttons in this sample appear to not work at all". The test `[dwc/06_IconPools/DownloadButton.bbj] issue #6: every button icon renders` is red, and the result file records:

- **0 of 8 icons render**, in every pool: feather 0/2, tabler 0/2, Font Awesome 0/2, ionicons 0/2. The same 0 of 2 for `Exercise-IconPoolsComplete.bbj` (tabler 0/1, fa 0/1). The screenshot shows eight text-only buttons.
- **The cause is the tag name.** The three samples write `<bbj-icon pool=... name=...>`. On BBj 26.03 the browser knows `dwc-icon` (`customElements.get('dwc-icon')` is defined) and does not know `bbj-icon` (not defined). The 8 and 2 elements in the page are inert: box 0 x 19 px, no shadow root, no SVG. The course page `07-icon-pools/index.md` writes `<dwc-icon>`; DWC2.bbj's `<dwc-icon name='speakerphone'>` renders (26 x 26 px).
- **The same markup works with the other tag.** Browser-only experiment (a throwaway container in the page, removed afterwards, the sample file unchanged): the same eight attribute sets written on `<dwc-icon>` give feather 2/2, tabler 2/2, Font Awesome 2/2 and ionicons 2/2. With the styled attributes in place the feather cloud icon becomes 44 x 44 px and danger red, the tabler cloud icon 13 px wide and green.
- **The custom pool has the same problem.** The sample registers `ionicons` in `window.BBj.IconsPools` (confirmed: the array holds `ionicons`). The DWC reads `window.Dwc.IconsPools`, which the page `07-icon-pools/index.md` uses; the experiment registered the ionicons 6.0.2 resolver there and both ionicons icons rendered. `window.Dwc.IconsPools` did not exist in the unchanged page, and on DWC2.bbj it lists `dwc`, `tabler`, `feather`, `fa` (no `bbj` pool, although the page lists one; that probe is not committed).
- **Network, recorded apart from the BBj result.** The unchanged sample makes 0 SVG requests, 0 requests to ionicons and has 0 failed requests (no element asks for an icon, so cdnjs is never contacted). During the experiment: 6 SVG requests to `cdn.jsdelivr.net` (the built-in pools load their icons from there) and 2 to `cdnjs.cloudflare.com` (ionicons 6.0.2), all HTTP 200. The page `07-icon-pools/index.md` names ionicons 7.4.0; the sample uses 6.0.2.
- **Styled variants (page "Size and color").** Because the element is inert, `expanse='l'` and `theme='danger'` do nothing (feather icon color is the button text color, `oklch(0.42 0.253545 263.526)`), while the inline styles do reach the empty elements (tabler computed color `rgb(0, 128, 0)`, Font Awesome computed color equal to the danger token) with nothing drawn.
- Fix candidates for Eric (not tried, D-03): change `bbj-icon` to `dwc-icon` in `DownloadButton.bbj` and the two exercise files, and register the pool in `window.Dwc.IconsPools` (the page's `injectScript` form; `executeScript` with the `Dwc` registry was only tried inside the browser experiment).

## Other findings

- **The email pattern of the exercise is invalid in Chromium.** The tip in `Exercise-BuiltInValidation.bbj` (line 78) and on `90-exercise-email-validation.mdx` is `^[\w!#$%&'*+/=\-?^_`{|}~]+(\.[\w!#$%&'*+/=\-?^_`{|}~]+)*@[\w-]+(\.[\w]+)*(\.[a-z]{2,})$` (with a typographic apostrophe). The browser compiles the `pattern` attribute with the `v` flag, where `/`, `{`, `|` and `}` inside a character class must be escaped, so it logs "Pattern attribute value ... is not a valid regular expression" ("Invalid character in character class") and ignores the pattern. The solution therefore has `required` (goal 1 works) but no pattern validation (goal 2 red): `abc` is a valid email. The zip pattern `(\d{5})(-\d{4})?` compiles and works.
- **The course page claims in chapter 08 hold.** Fields are pristine at the start; a field turns invalid only after it received a character and was emptied; a pattern field is valid when empty; spaces pass the form-level check of `formValidation.bbj`, and `trim()` makes the JavaScript validation stricter; `data-validation-auto-disable` disables Submit while a field is invalid. Client-side `required` blocks Submit before the server callback runs (0 message boxes).
- **SysPrint works now, the plan 09 smoke result does not reproduce.** The plan 09 smoke run (2026-10-09) recorded no window, console or dialog within 30 s. Today the program starts in 0.6 to 3.5 s in the behaviour test and passes smoke when run once more (dialog at 878 ms; the old result file was restored afterwards, the new one is kept as `results/probe/sysprint-smoke-plan13.json`, both ignored). The cause of the earlier timeout is not known (a cold first PDF print job is a guess); plan 16's baseline will show whether it comes back.
- **SysPrint delivers the PDF to a popup, not into the page.** At the moment the printer is closed the DWC opens a second browser page that requests `/printServlet/job<n>.pdf` (`application/pdf`, status 200) and logs `HidePrintPopupMessage`; the program then shows `msgbox("done!")`. The message box has no title argument, so DWC shows the program's file path as its title (a local path on the user's screen; not recorded in any result).
- **The file chooser cannot be driven through "Select Files...".** `dwc-upload` calls `window.showOpenFilePicker`; with Playwright's file chooser interception active the call fails with "AbortError ... Intercepted by Page.setInterceptFileChooserDialog()" (console warning) and no `filechooser` event arrives. Dropping a file on the control uploads it at once (no Upload click needed); the Upload and Cancel buttons stay unused. `BBjFileChooser.ON_FILECHOOSER_APPROVE` fires on the drop.
- **`fill()` appends in DWC edit boxes.** On the zip field `fill('abc')` produced `abc87109` (as plan 10 saw on a combobox), so the tests select all and type, or press Delete.
