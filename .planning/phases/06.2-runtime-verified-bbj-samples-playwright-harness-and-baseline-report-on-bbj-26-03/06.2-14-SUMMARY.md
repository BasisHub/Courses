## Findings

### ShoelaceSplitter.bbj: the child windows never reach the splitter

The page says the sample ends as "a splitter with two child windows, each hosting a full-size button" (red top panel, green bottom panel). On BBj 26.03 the window shows the splitter (divider, handle icon) empty in the middle, and the two buttons at the top left of the window, one under the other, outside it.

- **Cause (DOM evidence, sample unchanged).** The sample moves the child windows with `document.getElementById('<uuid>').appendChild(document.getElementById(top!.getAttribute("id")))`. In DWC the child windows are `dwc-panel` elements that have only a `dwc-id` attribute and no `id` attribute (checked on both panels), and the sample never calls `setAttribute("id", ...)` on them, which the page says to do first ("If you want to use `getAttribute("id")`, call `setAttribute("id", "your id here")` first"). `document.getElementById('')` returns null (checked), so the move cannot work. DWC catches the script error: no page error, no console error and no network problem appear.
- **What the slots look like.** The `sl-split-panel` has one child (`sl-icon[slot=handle]`); its shadow slots start, handle and end hold 0, 1 and 0 elements. The panels carry `slot="start"` and `slot="end"` and are children of `dwc-window-content`.
- **Browser-only probe (not in the committed test, nothing changed in the sample).** Appending the two `dwc-panel` elements to `sl-split-panel` by hand put them in the Start area (y 78) and the End area (y 310), each 760 px wide and 37 px high, so the Start and End areas do work once the panels are inside; the buttons fill the width, not the height of the area.
- Fix candidate for Eric (not tried, D-03): call `setAttribute("id", ...)` on both child windows before the script, as the page says, or look the panels up by another attribute.

### Exercise-MediaQueriesComplete.bbj: the font token changes, the font does not

The page (and the comment in the CSS) says that below 600px the form "uses a smaller font". The media query sets `--dwc-font-size: var(--dwc-font-size-s)` on `.contact-form`. At 500 px the custom property on the panel is `0.8125rem` (0.875rem at 1024), but the label, the edit box and the panel all compute 14px at both widths. None of the measured elements (label, edit box, panel) takes its `font-size` from the property: the body gets 14px from the root where the property is declared, and the elements below inherit that computed value, so a change of the property on a descendant has nothing to act on. With `font-size: var(--dwc-font-size)` set on the panel for a moment in the browser, the label computes 13px; a rule like that in the CSS file is a fix candidate (not tried, D-03).

UAT test 4 recorded "pass" for this exercise by hand. The harness agrees with every other part of that test (one column, no Company field below 600px, two columns at 600px and wider) and disagrees only on the font: a 1 px change of the token (14px to 13px) is hard to see even where it applies, and here it does not apply at all.

## Harness issues

None that blocked anything; nothing under `lib/` was changed.

- `page.requests()` keeps only the last 100 requests, and the Shoelace beta makes 135 on its own (2.20.1 up to 210), so the first requests of a library load are already gone when a test asks for them. The CDN watcher attaches `page.on('request' | 'response' | 'requestfailed')` at the start of the body and adds what `page.requests()` still has afterwards.
- A DWC message box wraps long text at a fixed column, also inside a word (`.../courses-dwc-0` then `9-eventmapsample` in the dump), so a check on a token of a long text must remove all whitespace first.
- `sl-rating` and similar Shoelace components take pointer events on an overlay above their parts; `locator.click()` on the inner icon waits and times out, so tests click the coordinates of the part.
- `note()` cuts each note at 200 characters and the wrapper cuts the evidence at 700, so the key facts of a red result go into the first notes (as plans 12 and 13 found).
- A DWC `dwc-htmlview` is not an iframe: its content is in the light DOM of the page (a canvas, buttons, inputs), so plain role locators work and `page.frameLocator` is not needed.
- `check-behaviour.mjs --prefix <p>` prints the number of all behaviour tests found (91), not the number under the prefix (as plans 10 to 13 noted).
