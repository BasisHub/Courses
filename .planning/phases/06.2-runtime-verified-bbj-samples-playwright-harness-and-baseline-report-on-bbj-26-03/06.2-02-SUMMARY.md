## Classification rules (category to trigger)

Reasons make a sample fail; warnings are recorded only. `blocked` is decided first and returns immediately with a single `license` reason.

| Outcome | Category | Trigger |
|---------|----------|---------|
| blocked | `license` | `start.state` is `license`; any dialog text matches `/E3008\|out of licenses/i`; or a dialog title starts with "License Error" |
| fail | `bbj` | a `!ERROR=n (...)` line in the console body or in any dialog text (detail carries the line and statement when the console gave them); also an `Error` dialog whose text has no readable `!ERROR=` code |
| fail | `console` | a dialog text matching `/break to console/i`; or, for `window`/`starter`, a console that shows READY with no BBj error ("program ended and returned to READY") |
| fail | `start` | `start.state` is `timeout`; for `window`/`starter` the state is not `window`; for `print` the state is not `console` |
| fail | `print` | `print` kind: an `expect.print` string is not a substring of any printed line |
| fail | `dialog` | `dialog` kind: no dialog with the expected title (and text, when set) |
| fail | `page` | a page error not matched by `IGNORED.pageErrors` |
| fail | `console-error` | a browser console error not matched by `IGNORED.consoleErrors` |
| fail | `network-local` | a failed request (error set) or HTTP 4xx/5xx to the local server, not matched by `IGNORED.network` |
| fail | `network-external` | the same for an external host |
| fail | `icons` | `icons.missing` is not empty (detail lists `pool:name` for each) |
| warning | `console-output` | `window`/`starter` with a console that has no READY yet (detail: printed lines joined by ` / `) |
| warning | `title` | `window`/`starter` with `expect.title` that differs from the observed title |
| warning | `console-warning` | every browser console warning |
| warning | `debug-log` | `debugLog.errorLines` greater than 0 |
| (never set by classify) | `timeout` | set by the test wrappers in plan 09 when a test body hits its deadline |

An unknown kind (anything but `window`, `starter`, `print`, `dialog`) throws.

### Hardening beyond the written rules (Rule 2, all covered by tests)

These tighten the written rules without changing any case the plan lists:

- `parseConsole` redacts the serial from every line before parsing, so `header`, `body`, `printed`, error messages and statements cannot leak it even if the header split is wrong (T-06.2-06).
- The header split guards against a console with no blank line after the header: when the candidate header would contain an `!ERROR=` line, the header becomes the leading run of lines that match `HEADER_PATTERNS`. Plan 08 still has to confirm the real header layout live.
- The `!ERROR=` regex accepts a missing parenthesised message (`!ERROR=14` alone gives message `''`), so such an error is not silently skipped.
- An `Error` dialog with no readable `!ERROR=` code still fails with category `bbj`; without this it would have passed.
- The break-to-console dialog gives `console` only, not also `bbj`.
- A network entry fails only when `error` is set or `status` is 400 or above; the plan said "network entries" without defining a failure, and counting a 200 entry as a failure would be wrong.

### Interpretation worth knowing

- `makeSampleResult` and `makeBehaviourResult` throw when `status` or `outcome` is missing, not only when it is invalid. The contract types both as one of `pass|fail|blocked` (never null), so a result without a verdict is a bug. Later plans that build a result must pass the verdict.
