## The exercise solutions lose their layout

Both solutions build a `JsonObject` and apply it with `window!.setPanelStyle("@element", json!.toString())` (Flexbox lines 24 to 32, Grid lines 21 to 30). DWC logs one console error per program and the JSON properties never reach the panel: computed `display: block`, no padding, no gap, controls in flow layout. Exact message from the smoke results (identical for both samples, plan 09 run on the same server; the behaviour runs confirm its first sentence in their notes):

- `Exercise-ConvertToCssFlexboxComplete.bbj` and `Exercise-ConvertToCssLayoutComplete-Grid.bbj`: "Starting from BBj v24.00, the style directives are no longer available. Instead, their equivalent can now be found in BBjWebManager. For more information, please refer to the BBjWebManager documentation at https://documentation.basis.cloud/BASISHelp/WebHelp/bui/BBjBuiManager/bbjbuimanager.htm."
- `DWCGrid.bbj` (line 145, `window!.setAttribute("@app-style", css!)`): "Starting from BBj v23.00, the attributes directives are no longer available. Instead, their equivalent can now be found in BBjWebManager. Check the migration guide: https://basishub.github.io/basis-next/#/dwc/guide/attributes-directives". It has no visible effect there: the layouts reach the page through `injectStyle` (lines 95 and 264), all nine behave as the page says.

The per-property form does work in this chapter. A probe round (stored in the ignored `results/probe/ch05-DWCGrid.bbj.json`, not a test) showed that `DWCGrid.bbj`'s `window!.setPanelStyle("display", "grid")` and its siblings (lines 37 to 42) end up as the inline style of the panel (`width: 100%; box-sizing: border-box; display: grid; grid-template-rows: max-content minmax(16em, 1fr); gap: 1em; padding: 1em;`), and `setStyle` on a control or child window works too (the flexbox preview and the Submit button's `grid-column: 1 / 3`). Only the JSON `"@element"` form is dropped. Nothing was tried that would change a sample (D-03).

The Submit button of the grid solution shows the consequence the page cares about: `grid-column: 1 / 3` is set on the button, but because the panel is not a grid it has no effect, and the button sits in the flow at 113 px width.

## Runtime evidence: the void assignment (lines 36 to 38)

`bbjcpl -t` flags `myName! = window!.addEditBox("Joe Blow").setAttribute("label", "Name:")` in `Exercise-ConvertToCssFlexboxComplete.bbj` (and the same three lines of the starter): "Autocast will always fail on assignment from void to com.basis.bbj.proxies.sysgui.BBjEditBox". At runtime:

- **The sample runs.** The window opens, no BBj `!ERROR` appears in the console (the wrapper checks after every body), and all three `dwc-field` elements carry their label attributes and values. `setAttribute` still does its work; only its result is lost. The test `the form shows Name:, Company: and Email: ...` is green.
- **What the variables hold.** A one-off probe program in `tools/sample-test/fixtures/` (deleted again, never committed; the BBj compiler gave the same type-check message for it) copied the statement with `declare auto BBjEditBox myName!` and tested the variable. Result in a DWC window: the variable is `null` after the assignment (`if myName! = null()` is true). Calling a method on it, `myName!.setText("after")` at line 13 of the probe, stops the program with `!ERROR=252 Attempt to invoke method 'setText' on null object at line 13`. With an `err=` branch the same call reports error 252.
- **What it breaks.** Nothing in this sample: `myName!`, `myCompany!` and `myEmail!` are declared (lines 48 to 50) but never read again. It would break any program that used the variable after the chained call, for example to read or change the edit box. The exercise page teaches the chain as a feature ("chains `setAttribute()` to give each edit box a label in one line of code"); the lines work only as long as the result is discarded.

The same pattern is in the starter `Exercise-ConvertToCssFlexbox.bbj` lines 47 to 49 (covered by smoke and plan 13).

## Runtime evidence: injectLinkUrl with whole `<link>` tags

`DWCFlexbox.bbj` lines 469 to 471 and `DWCFlexbox.BBj24.bbj` lines 396 to 398 call `web!.injectLinkUrl("<link rel='preconnect' href='https://fonts.googleapis.com'>", 1)` and two more calls of the same form. The first argument of `BBjWebManager::injectLinkUrl` is a URL. In both programs the browser shows:

- 3 `<link>` elements in the head besides `dwc-ui.css`, each with an empty `rel` and an `href` that holds the whole tag text (`<link rel='preconnect' href='https://fonts.googleapis.com'>`, the gstatic one, and `<link href='https://fonts.googleapis.com/css2?family=Inconsolata&...' rel='stylesheet'>`).
- No request to those hrefs: of 31 requests seen in `DWCFlexbox.bbj` and 29 in `DWCFlexbox.BBj24.bbj`, none went to fonts.googleapis.com or fonts.gstatic.com, and none had a link tag in its URL. A link element without `rel` fetches nothing, so there is no 404 and no network finding either (smoke recorded none).
- Consequence: the Google fonts Inconsolata and Ubuntu Mono never load. Nothing visible depends on it: the program's CSS uses `--dwc-font-family-mono`.
