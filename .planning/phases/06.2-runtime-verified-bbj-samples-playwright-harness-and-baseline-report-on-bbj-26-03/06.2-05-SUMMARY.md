# Phase 06.2 Plan 05: Session lifecycle for Playwright runs

**A Playwright run now takes the run lock, snapshots and sweeps BBj sessions, registers 63 `courses-*` apps in one Admin API call, terminates every session each test creates, and on teardown sweeps, removes all apps and releases the lock; proved live with three selftests and `CLEAN` afterwards.**

## Performance

- **Tasks:** 2 of 2
- **Files created:** 7, modified: 1 (all under `tools/sample-test/`; nothing under `docs/` changed)
- **Live runs:** four full runs on BBjServices 26.03 (two plain selftest runs, one with a deliberately failing test, one more after the teardown fix), plus two failed-setup scenarios. Each ended with `node cleanup.mjs` printing `CLEAN`.

Both numbers include the roughly four seconds a Java source launch takes, so 63 apps cost only 10 to 14 seconds on top of that. The plan's fear of "minutes" for about 63 apps did not materialise.

Selftest timing (final run, test durations as the list reporter prints them): test 1 (fixtures registered) 3.7 s, test 2 (known-good opens a DWC window) 4.2 s, test 3 (no session left) 3.1 s. The first run was 3.5, 6.2 and 3.0 s. These durations do not include the `bbj` fixture's own setup and teardown. Wall clock for the whole `npx playwright test --project=selftest` is 55 to 67 s (59.8 s in the final run).

Cost to plan with: every Admin API call is a fresh Java source launch, measured afterwards at 4.1 to 4.5 s for `status` and 4.2 s for `apps`. A test that uses the `bbj` fixture makes at least three `status` calls (license wait, the session snapshot, the check after the test), about 13 s of fixture overhead per program, and more when a leftover needs a second look. For the 59 runnable samples that is about 13 minutes of overhead before any program-specific waiting. If plan 09 or 16 finds that too slow, the cheap saving is to let `waitForLicense` hand back the process list it already read, so the snapshot needs no extra call.

## Observed PROGRAM_NAME format

`status` reports the program of a session exactly as registered: a forward-slash absolute path with an upper-case drive letter and the checkout's own letter case, for example `C:/Users/<user>/Documents/git/Courses/tools/sample-test/fixtures/known-good.bbj`. No backslashes, no doubled slash, no file-name-only form, so the anchored W9 prefix match in `isHarnessSession` needed no change. The selftest asserts that the session of the open program is a new harness session, so a different format in the future fails loudly instead of silently leaking a license. `lib/admin.test.js` has a new test that runs every registered program path of `allApps()` through `isHarnessSession` with the default roots.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Teardown would have cleaned up while another run held the lock**
- **Found during:** Task 2, while testing the failed-setup path
- **Issue:** the first draft of `global-setup.js` cleaned up after its own failure, assuming Playwright skips the teardown then. Playwright 1.64.0 does not skip it: `createGlobalSetupTasks` registers the teardown as its own task in front of the setup task, so it runs after a failed setup. The visible symptom was a second error and a double teardown. The real hazard: if the setup fails because the lock wait timed out, the teardown would still `sweep()` and `unregister('courses-')` while the run that holds the lock is working.
- **Fix:** the teardown returns at once unless `COURSES_RUN_ACTIVE` is set, which the setup does right after it holds the lock; the self-cleanup in the setup is removed; the credential check moved in front of `acquireLock` (a small reorder of plan steps 1 and 2, so a missing key fails without any side effect).
- **Files modified:** `tools/sample-test/global-setup.js`, `tools/sample-test/global-teardown.js`
- **Verification:** the two failure scenarios above, then a full passing run
- **Commit:** `22a0bcb`

### Additions beyond the plan

**2. [Rule 2 - Missing critical functionality] Fixture re-check loop and `no-license` annotation**
- The plan's fixture terminates once and re-checks once. `cleanup.mjs` already learned (plan 01) that a terminated session can stay listed for a moment, so the fixture terminates, waits one second and looks again up to two more times before it annotates `leftover-session`. With `workers: 1` and 3 licenses a spurious leftover would fail later tests for no reason. When no license is free, the fixture also adds a `no-license` annotation so the report can say why.
- **Files:** `tools/sample-test/lib/fixtures.js` | **Commit:** `c0ddbc1`

**3. Program-name pin in `lib/admin.test.js`.** The plan asked for a unit test only if the observed format needed normalisation. It did not, but the live format is now pinned against every registered path anyway (see above).
