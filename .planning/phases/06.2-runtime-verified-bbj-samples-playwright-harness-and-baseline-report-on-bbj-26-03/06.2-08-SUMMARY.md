## Live-confirmed DWC details

Everything the plan listed as "undocumented DWC internals" was checked on BBj 26.03 with a probe spec that was deleted before any commit.

**Console buffer access.** `document.querySelector('.dwc-console__xterm')` is in the light DOM (its tag is `dwc-window-center`). Both `host.xterm` and `host.widgetManager.terminal` return the xterm.js Terminal; `term.buffer.active.getLine(i)` with `translateToString(true)` and `isWrapped` reads the rows. Rows are padded with real space characters to 80 columns, so `translateToString(true)` does not trim them: `readConsole` trims each joined line.

**Console header layout (in words).** Seven lines and no blank line after them: the title, the server version, the server build, the client version, the client build, one line with the license serial number (the sixth line), and a copyright line. Program output starts on the very next line. After the program ends there is a blank line, then `READY`, then a line holding only the `>` prompt. The plan 02 rule ("header ends at the first blank line") misread this: for print programs it swallowed the printed lines into the header, and for error programs it left build lines in the body. `parseConsole` now ends the header at the copyright line (title line first, copyright within 12 lines), falls back to the leading run of header-pattern lines otherwise, trims padding, and treats everything after the last `READY` as prompt.

**Dialog structure.** A BBj `msgbox` is a `dwc-dialog` (attributes `type="msgbox"`, `theme="info"`, `opened`, no `label`) that covers the whole viewport. Its light DOM has three slotted parts: `header[slot=header]` whose first child div holds the title (the second holds a `dwc-icon`), `section[slot=content]` with the message text, and `footer[slot=footer]` with one `dwc-button` per button (label is its light-DOM text; the inner `button` has an empty aria-label). `readDialogs` returns `{ title: 'Fixture', text: 'Hello fixture', buttons: ['OK'] }`. `getByRole('button', { name })` inside the dialog finds the button; after the click the `dwc-dialog` element is removed from the DOM (count 0).

**Panel element.** `dwc-window-content` itself carries the panel style set with `setPanelStyle`. On `DWC2.bbj` it computes `display: inline-grid`, `gap: 5px`, `padding: 15px`. The default selector stays. Note for the issue tests: computed `grid-template-columns` is resolved to pixels (`94px 188px` for the source value `1fr 2fr`, ratio 1:2), so compare ratios, not the source string. Its ancestors are `dwc-window-center`, `dwc-window-container`, `dwc-frame`, `dwc-frame-manager`.

**Icon rendering.** A rendered icon is a `dwc-icon` host with a bounding box of at least 4 x 4 px whose open shadow root holds `div[part=control][role=img]` with an `svg` that has child elements (paths). `DWC2.bbj`'s speakerphone icon is 26 x 26 px with `pool="tabler"` (the component sets the attribute even though the BBj markup gave none). A deliberately unknown icon name, injected into the browser page only, gives a 24 x 24 host whose control div is empty: `iconReport` lists it as `{ pool: 'tabler', name: 'no-such-icon-zzz' }`, so the "missing" rule works. `DWC2.bbj` also contains four hidden `dwc-icon` elements of DWC's own (chevron up and down in pool `dwc`, 0 x 0 box, `checkVisibility()` false); they count in `total` and in neither `rendered` nor `missing`.

**Dark theme.** Setting `data-app-theme="dark"` on the document element changes the rendering: the known-good PNG files are 7375 bytes (light) and 7622 bytes (dark). The attribute is absent in the light state and removed again afterwards.

**Other signals.** `--dwc-color-primary` is a multi-line `oklch(from hsl(...) ...)` expression, so `cssVar` collapses whitespace. A known-good page has no `dwc-icon` at all until a dialog opens (the dialog brings its own info icon).

## Issues Encountered

- **Line endings.** `lib/console.js`, `lib/console.test.js` and `lib/classify.js` had CRLF endings in the working copy (`core.autocrlf=true`, the index holds LF). I normalised the first two to LF before editing (the same step plan 05 took for `admin.test.js`) and restored `classify.js` with `git checkout` because only its line endings had changed. Git prints `LF will be replaced by CRLF` warnings on commit; that is the autocrlf setting.
- **Hung probe.** One of my own diagnostic scripts (a direct Playwright script, not committed) left its browser open and did not exit. I stopped exactly that process tree by its process ID (the user's own Chrome processes were left alone), freed any session it held by ID, and confirmed 0 BBJ licenses in use and no `courses-*` app before continuing.
- **License-leak simulation.** The first attempt (a copy of known-good outside the harness roots, opened in the fixture's own page) showed no leak because the license came back within the fixture's wait after the page closed. The second attempt held the connection open from a second browser the fixture does not own: the fixture flagged the result file `harnessIssue: "license-leak"` with the leaked session id and program, added a `license-leak` annotation, and did not terminate the foreign session (the rule `isHarnessSession` is false for that path, checked directly). The probe then freed the session by ID. The probe files were deleted and not committed.
- **Shell quoting.** Backslash escapes are collapsed in heredocs of this shell tool, so two throwaway scripts were written with the file tool instead; no committed file was affected.
